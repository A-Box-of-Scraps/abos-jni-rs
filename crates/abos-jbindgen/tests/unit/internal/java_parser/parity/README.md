# Source/class-file/JAR parity

Run `mise run test:abos-jbindgen:parity` for the metadata, parser-diagnostic, and generated-binding runtime tests. These
tests also run through `mise run test:abos-jbindgen` and the standard `mise run test` task.

## Contract

`tests/support/parity.rs` lists the shared Java fixtures and their binary-name selection patterns. The metadata runner
compiles that batch once into a temporary directory, packages those exact bytes into a JAR, and independently parses
source, class files, and JAR entries. Each inventory must match the handwritten expectations in `expected.rs`.
Source/bytecode equality alone is insufficient: a shared omission must fail too.

The comparison checks:

- Exact class inventory and binary names, with duplicate classes rejected.
- Direct superclass and interface relationships, excluding `java.lang.Object` consistently with the binding model.
  Inherited methods are not copied into the subclass's declared-member inventory.
- Constructor and method names, complete JVM descriptors (including return types), and static/native/public flags.
- Field names, descriptors, and static/final flags.
- Duplicate members, including duplicate signatures carrying different flags.
- Java parser descriptor fields independently of their conversion to Rust metadata, including native methods.

Non-private constructors, ordinary methods, and fields are included. Private ordinary members are excluded; private
native methods remain in metadata for native registration. Visibility expectations include protected and package-private
members, although the intermediate representation distinguishes public from non-public, not every Java access modifier.

Ordering, parameter names, and documentation are not runtime API differences. Source-only binding annotations are
intentionally absent from this fixture batch: `generation.rs` separately checks skip/name/primitive annotation behavior.
An annotation that changes member selection is not silently normalized away.

## Compiler-generated differences

`expected::artifacts` declares exact owner/name/descriptor/access-flag entries for enclosing-instance fields, enum
implementation members, and covariant/generic bridge methods. Raw class-file metadata must match this inventory before
normalization. Unexpected artifacts, changed flags, and missing expected artifacts all fail. No name-only or blanket
synthetic-member filter is permitted. These expectations are verified with the JDK pinned in `mise.toml`; compiler
upgrades require review if implementation artifacts change.

`EnumTypes$1`, the anonymous implementation of `BLUE`, is the sole extra compiled class. Its presence is asserted, but
it is not treated as a separately named source declaration. Bytecode generation still includes it. Bridges are excluded
only from the declared-API comparison: generated bytecode bindings retain them, and runtime assertions invoke both
bridges explicitly. Record accessors and enum `values`/`valueOf` are part of the expected API, not exceptions.

## Coverage and execution

| Fixtures                                            | Contract and runtime coverage                                                                             |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `GenericTypes`                                      | Unbounded, dependent, recursive, intersection and shadowed bounds; generic methods; arrays; erasure       |
| `EnclosingTypes`                                    | Static/non-static nesting, immediate enclosing constructor parameters, implicit constructors, inheritance |
| `RecordTypes`, `Marker`, `EnumTypes`                | Nested records/annotations/enums, generated members, constants, annotation values, typed arrays           |
| `Overloads`, `ParityMembers`                        | Overloads with distinguishable results, static/instance methods, mutable/final fields, primitive arrays   |
| `ParityVisibility`                                  | Constructor visibility, protected/package access, excluded private members, native/public metadata        |
| `ParityInheritance`                                 | Generic override bridges, covariant returns, inherited calls and interface defaults                       |
| `DefaultType`, `DefaultPeer`, `I`                   | Default package, cross-class references, single-letter names and object-array descriptors                 |
| `Identifiers`, `keywords/match`, `UnsupportedNames` | Unicode, dollar signs, Rust keywords and normalized-name collisions                                       |

The standalone runtime crate compiles its fixture batch once and generates separate source and JAR modules without
cross-mapping the parity wrappers. Both modules initialize against the same compiled classes. Shared assertion bodies
exercise both paths; a small explicit naming adapter handles the extra overload caused by a bridge. Native visibility is
checked as metadata; the visibility fixture's unimplemented native methods are not invoked.

The integration test builds the executable once, then runs eight named scenarios in separate JVM child processes under
`-Xcheck:jni`. Each child has a 120-second execution limit and captured diagnostics. The default standalone invocation
runs every scenario for convenience. The runtime build and metadata test have separate temporary artifacts; they do not
share a mutable cross-test cache.

Comparator tests deliberately introduce shared omissions, changed descriptors/modifiers/parents, duplicate members, and
unapproved or stale compiler artifacts. Existing parser tests require clear errors for selected local classes and verify
generation succeeds when unsupported declarations are excluded.

To add coverage, add a focused fixture or extend an existing one, update the shared inventory and independent expected
API, then add paired runtime assertions. Do not regenerate expectations from either parser or weaken normalization to
make a discrepancy pass. Windows/Android execution and other JDK versions are not established by the Linux JDK 25 run.
